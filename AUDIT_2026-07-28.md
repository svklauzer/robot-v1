### Цепочка входа (`RobotLoop.step`)

```
analyze_symbol → action≠hold → setup_decision=approve → TRADEABLE_REGIMES
  → ALLOW_SHORTS → entry_zone (книга) → grade → should_publish
  → post-loss cooldown → depth-гейт (стакан + LiquidityGuard)
  → build_plan → symbol_performance_guard → production_entry_gate
  → symbol_policy → RSI late-entry → exposure_guard → anti_drain
  → reentry_cooldown → ML-контроллер → conviction sizing → Signal(published)
```

### Цепочка выхода (`SignalLifecycleManager`)

```
published → цена в зоне → freshness → open_paper_position → opened
opened → hard stop | low_grade_release | exit_policy.before_tp1 | TP1
TP1    → частичная фиксация 50% + стоп на breakeven → tp1
tp1    → hard stop | TP2 | exit_policy.after_tp1 → closed
closed → CostEngine net PnL + TP1-часть → ML-лог → Telegram
```

Цепочка логически замкнута; MFE/MAE/траектория пишутся в `plan_json.lifecycle`, поэтому replay и walk-forward работают на фактических данных.

## 4. Блокеры

### B0 · Система считает деньги как swap, а торгует как spot — **корень проблемы**

`ENABLE_FUTURES_EXECUTION=true` ⇒ `execution_market_type = "swap"`. Это значение подставляется в **модель издержек**:

- `CostEngine.estimate(market_type=settings.execution_market_type)` → `FUTURES_TAKER_FEE = 0.05%` + funding-буфер;
- `exit_policy._fee_rate()` → та же swap-ставка → пороги `net_safe`, `protect_start`, `trail_start`, breakeven-буфер;
- `trade_plan.build_plan` → `net_pnl_*`, `net_rr_*` → гейты `anti_drain`, `production_entry_gate`, `symbol_policy`.

Но **всё остальное — спот**:

| Слой | Что используется | Факт |
|---|---|---|
| ccxt-инстанс | `options.defaultType = HTX_MARKET_TYPE` | `spot` |
| Символы | `HTX_SYMBOLS` = `BTC/USDT`, `ETH/USDT`, … | спотовые unified-символы; своп в ccxt — `BTC/USDT:USDT` |
| OHLCV / тикеры | `fetch_ohlcv("BTC/USDT")` | спотовые свечи |
| Стакан | `wss://api-aws.huobi.pro/ws`, `market.btcusdt.depth.step0` | **спотовый** WS (у свопа `/linear-swap-ws`) |
| Точность и мин. лот | `amount_to_precision("BTC/USDT")` | из спотового рынка |
| Ордер | `LIVE_EXECUTOR.place_market("BTC/USDT", market_type="swap")` → `create_order("BTC/USDT", …)` | ccxt разрешит символ в **спотовый** рынок; `params.defaultType` этого не меняет |

`funding_arbitrage` делает правильно — там есть `FundingSymbolMapper.swap_symbol()` → `BTC/USDT:USDT`. В трендовом движке такой конвертации **нет ни одной**.

**Последствия сейчас (paper/dry-run):** round-trip издержки занижены примерно вчетверо — 0.1% вместо 0.4%. Это не косметика: `anti_drain` судит сделку по `net_rr_tp2` и `min_edge_after_costs_usdt`, `exit_policy` вычисляет `net_safe_floor` (0.30% для деривативов против 0.60% для спота). То есть **вся накопленная статистика прибыльности, все RR-гейты и все пороги защиты стоят на заниженной себестоимости.** Решение «выходить в live» опирается на цифры, которые не воспроизводятся на реальном рынке.

**Последствия в live:** ордер уйдёт на спот. Шорт (`ALLOW_SHORTS=true`) на споте невозможен — это будет продажа актива, которого нет. `reduceOnly=True` спот-эндпоинт отвергнет. `_ensure_leverage` выставит плечо на своповом рынке, который не торгуется.

**Решение — выбрать одно:**
- **A (торгуем своп, как задумано):** конвертировать символ в `:USDT` на всех путях исполнения и рыночных данных, перевести WS на `linear-swap`, `HTX_MARKET_TYPE=swap`;
- **B (торгуем спот):** `ENABLE_FUTURES_EXECUTION=false`, `ALLOW_SHORTS=false`, пересчитать историю по спотовой ставке 0.2% и заново оценить, остаётся ли edge.

Пока это не решено, остальные пункты вторичны.

### B1 · `POST /telegram/webhook` — бесплатный VIP одним HTTP-запросом

Дашборд закрыт: `BASIC_AUTH_USER=Finmt` / `BASIC_AUTH_PASS` на `robot-web` заданы, middleware работает. Но **`robot-api` доступен напрямую**, и у него есть ровно один неаутентифицированный маршрут — `POST /telegram/webhook`. Проверок нет никаких: ни `X-Telegram-Bot-Api-Secret-Token` (Telegram его поддерживает через `setWebhook`), ни IP-allowlist подсетей Telegram, ни rate-limit, ни подписи.

**Вектор 1 — активация платной подписки без оплаты.**

```
POST https://robot-api-1rgi.onrender.com/telegram/webhook
{"message":{"chat":{"id":"123"},
            "successful_payment":{"invoice_payload":"vip:1",
                                  "telegram_payment_charge_id":"x"}}}
```

`_handle_successful_payment` вытаскивает `payment_id` из строки `vip:<id>` и зовёт `BillingService.confirm_payment(payment_id=…)`. Внутри — никакой верификации провайдерского события: платёж просто помечается `paid`, подписчик переводится в `active` на `duration_days` тарифа. `provider_event_id` пишется, но не проверяется и не сверяется с Telegram. `payment_id` — последовательный integer, значит перебор `vip:1…vip:N` активирует все висящие платежи. Свой платёж атакующий создаёт тем же вебхуком: `/plans` → `/pay` → инвойс.

**Вектор 2 — генерация VIP-инвайтов.**

`HTX_AFFILIATE_VERIFY_ENABLED = False` (дефолт, в Render env не переопределён). Значит:

```
{"message":{"chat":{"id":"X"},"from":{"id":"X"},"text":"/affiliate-registered"}}
```

сразу вызывает `activate_htx_trial()` и в ответ бот отправляет **одноразовую ссылку-приглашение в VIP-канал** (`create_single_use_invite`). Повторять можно с любым `telegram_user_id`.

**Вектор 3 — DoS.** Каждый запрос открывает сессию БД и уходит в Telegram API; ограничений нет.

Насколько эндпоинт «известен»: хост `robot-api-1rgi.onrender.com` захардкожен в `render.yaml`, который лежит в репозитории `github.com/svklauzer/robot-v1`. **Проверьте, приватный ли репозиторий.** Даже если приватный — имена сервисов Render перечислимы, а `matcher` middleware явно исключает `_next/static`, то есть статические чанки `robot-web` отдаются без Basic Auth.

**Фикс (по убыванию срочности):**
1. `setWebhook(secret_token=…)` + проверка заголовка `X-Telegram-Bot-Api-Secret-Token` в начале хендлера — 10 строк, закрывает все три вектора.
2. В `confirm_payment` — идемпотентность и верификация: отклонять, если `provider_payment_id` уже использован; принимать только платежи в статусе `pending`; сверять `total_amount`/`currency` из `successful_payment` с суммой платежа.
3. Ограничить приём по подсетям Telegram (149.154.160.0/20, 91.108.4.0/22) и добавить rate-limit.
4. Отдельно (харденинг): сделать middleware `robot-web` fail-closed при `APP_ENV=production` — сейчас удаление одной переменной окружения молча открывает дашборд, и об этом ничто не сообщит.

### B2 · Гейт зоны входа никогда не срабатывает — `workers/robot_loop.py:242`

```python
if not _ez.allowed:
    self.decisions.record(...)   # AttributeError: у RobotLoop нет .decisions
    db.flush()
    continue                     # ← сюда управление НЕ доходит
except Exception as exc:
    print(f"[ENTRY ZONE ERROR] {symbol}: {exc}")
```

`RobotLoop.__init__` не создаёт `self.decisions` и не импортирует `DecisionEventService` (в `SignalLifecycleManager` — создаёт, отсюда рассинхрон). Строка внутри `try/except Exception`, `AttributeError` глотается, `continue` не выполняется — **кандидат, отвергнутый зоной входа, открывается**. Признак: событие `entry_zone_support_too_far` в ленте решений не появлялось ни разу. Depth-движок включён, значит гейт активен и промахивается на живых данных.

**Фикс:** `self.decisions = DecisionEventService()` в `__init__` + импорт.

### B4 · `ML_MODE=shadow` молча режет размер позиции вдвое

Документированный контракт `MLController`: *«shadow — считает ml_score и отдаёт для ЛОГИРОВАНИЯ; на сделки НЕ влияет»*. Фактически в shadow возвращается настоящий `ml_score`, а `robot_loop.py:955` его использует **независимо от режима**:

```python
if bool(getattr(settings, "ML_SIZE_ALLOC_ENABLED", True)) and _ml_score is not None:
    _ml_mult = 1.0 if float(_ml_score) >= 0.45 else 0.5
_conv = min(_grade_mult, _ml_mult)
plan.qty *= _conv;  plan.required_margin *= _conv;  net_pnl_* *= _conv
```

`ML_SIZE_ALLOC_ENABLED` по умолчанию `True`. Итог: при `ml_score < 0.45` позиция урезается вдвое **прямо сейчас, на проде**, хотя владелец считает ML отключённым от денег. Shadow-валидация при этом сравнивает предсказания с исходами сделок, размер которых сам ML и изменил, — контур замкнулся сам на себя, и `/ml/shadow-report` измеряет уже не то, что должен.

**Фикс:** гейтить `ML_SIZE_ALLOC_ENABLED` режимом (`advisory`/`full_auto`), либо в shadow возвращать `ml_score` в отдельном поле, не читаемом сайзингом.

### B6 · Расхождение бумаги и биржи при неудачном live-ордере

`execution_engine._submit_live` при `res.ok == False` **только пишет ERROR** и продолжает:

```python
if not res.ok and LIVE_EXECUTOR.is_live():
    log_event(..., note="состояние робота и биржи разошлись, требуется вмешательство")
```

Ни отката, ни kill-switch, ни алерта владельцу. Позиция есть в БД и нет на бирже; все последующие `reduceOnly`-выходы уходят в пустоту.

Дополнительно: `LIVE_MAX_ORDER_NOTIONAL_USDT = 25.0` (дефолт) против типового нотионала `950 × 0.13 ≈ 123`. В live `production_blockers()` это поймает и не даст стартовать — механизм есть и работает. Но в **dry_run** кэп не блокирует, поэтому сейчас логи ровно об этом и предупреждают на каждой сделке.

### H2 · Жёсткий лимит 3 сделки в сутки

`MAX_TRADES_PER_DAY = 3` (дефолт, нигде не переопределён). `LiveSafetyService` считает сигналы `opened/tp1/closed` за 24 ч и при `>= 3` блокирует `robot_loop` целиком (`robot_loop_safety_skip`). Ведение уже открытых позиций продолжается — `background_manage_loop` проверяет только `bot.status`, — но новых входов нет. Если это не осознанное решение, система работает примерно на десятую долю задуманной активности, и накопление статистики для `VALIDATION_MIN_CLOSED_SIGNALS=50` растягивается на недели.

Frontend-job: `npm ci` с `cache-dependency-path: apps/web/package-lock.json`, а **`package-lock.json` в репозитории нет** → шаг падает всегда. `tsc --noEmit` и `npm run build` помечены `continue-on-error: true` → фронтенд не проверяется ничем.

### H4 · Блокирующая сеть в event loop — сценарий, который уже убивал инстанс 26.07

В коде есть развёрнутый разбор инцидента (`#egress-guard-2026-07-26`), и `analyze_symbol` вынесен в `to_thread`. Остальные пути не тронуты:

| Место | Что делает | Частота |
|---|---|---|
| `background_manage_loop` → `process_open_signals` → `market.snapshot()` | `fetch_ticker` + `fetch_ohlcv(5m, 200 свечей)` — 2 HTTP **на каждый сигнал** | **каждые 10 с** |
| `background_robot_loop` → `loop.step` → та же `process_open_signals` | то же | 60 с |
| `background_funding_arb_loop` | `scan` / `auto_open_candidates` / `evaluate_exits` — синхронно | по интервалу |
| `background_venues_spread_loop` | `VenueCompareService().compare()` — HTX + Kraken | 1 ч |

При 5 активных сигналах — 10 блокирующих HTTP-вызовов каждые 10 секунд внутри event loop. Отдельно: `market.snapshot()` тянет 200 пятиминутных свечей ради одного поля `snap["last"]`; рядом лежит готовый `ticker_snapshot()` — один вызов.

### H5 · Health-страница даёт нагрузку, сравнимую с торговым циклом

`app/health/page.tsx`: `setInterval(loadAll, 5000)` → `/system/health` + `/system/readiness`.

Один вызов `/system/readiness`: двойной полный скан `signals` (analytics + validation gates), скан `payments`, чтение `trade_outcomes.jsonl`, `MarketConnectivityService().check()` → HTX, `ExchangeReconciliationService().check()` → HTX, `FundingArbEngine().summary()` → HTX по каждой открытой позиции.

Одна открытая вкладка ≈ 12 обращений к HTX в минуту плюс постоянные full-scan к Postgres на плане basic-256mb. Риск сорвать rate-limit и разомкнуть circuit breaker для торгового цикла.

## 6. Средний приоритет

**M1 · Пред-проход динамической маржи считает не тех кандидатов.** `_ready_candidate_check` не применяет ни `TRADEABLE_REGIMES`, ни проверку зоны входа. Как только B3 починят, `ready` окажется завышен → `per_trade_margin` делит свободную маржу на кандидатов, которые не торгуются → систематически заниженный размер позиции.

**M2 · Расхождение qty.** `Order.qty = amount_to_precision(plan.qty)`, `Position.qty = plan.qty` без округления. PnL считается по позиции, биржа исполнит округлённое.

**M3 · Наблюдаемость циклов.** `/system/health` отдаёт 5 циклов из 13, `/robot/loop-state` — 3. Grid, manage, digest, ml_retrain, egress-монитор, walk-forward, venues в UI не видны: упадёт такой цикл — на Health будет зелено.

**M4 · Мёртвый код.** Не импортируются нигде: `services/risk_engine.py`, `recovery_engine.py`, `leverage_engine.py`, `analytics_service.py`. Пустые файлы (0 байт): `routers/{auth,bot,health,positions,signals}.py`, все `schemas/*.py`, `models/{alert,analytics}.py`, `workers/{health,report,sync}_loop.py`, `core/redis.py`, `telegram/bot.py`, `components/{EquityChart,HealthPanel,PositionsTable,Sidebar,SignalsTable,StatCard,Topbar}.tsx`. Плюс `apps/api/main.py.bak` и ~130 устаревших remote-веток `codex/*`.

**M5 · Легаси-путь живого ордера.** `ExecutionEngine.execute_signal(mode="live")` зовёт `client.create_market_order` напрямую — без идемпотентности, кэпа нотионала и подтверждения филла. Сейчас не вызывается, но лежит в файле, который правят чаще других.

**M6 · Размер файлов.** `main.py` — 153 КБ / 3900 строк, `core/config.py` — 150 КБ / 1000+ настроек, `services/market_intelligence.py` — 98 КБ. Поломка контракта авторизации при выносе роутеров — прямое следствие: тест был привязан к монолиту.

**M7 · Код расходится с комментарием.** `render.yaml`: «CROSS_FARB — дефолт выключен»; в коде `CROSS_FARB_ENABLED: bool = True`, и cross-venue paper-арбитраж работает.

## 7. Что сделано хорошо

- **`LiveExecutor`** — `clientOrderId`, сверка по нему при неоднозначном сбое (не удваивает позицию), поллинг реального филла, потолок плеча, кэп нотионала, режимы `off/dry_run/live` с понижением `live→dry_run` без `ENABLE_LIVE_ORDERS`.
- **`HTXClient`** — circuit breaker с ротацией хостов, class-level кэш рынков, backoff fee-API, принудительный IPv4. Инцидент 26.07 закрыт архитектурно.
- **`phantom_fill.py`** — честный PnL отдельным слоем: система умеет признать, что часть исторической прибыли была ошибкой книжки, и не опирается на неё.
- **`production_blockers()`** — реально работающий предполётный чек, включая ловушку `LIVE_MAX_ORDER_NOTIONAL_USDT` ниже типового нотионала.
- **`MLController._mode()`** — авто-деградация `full_auto → shadow` при `val_auc < 0.55`. Правильная идея: модель теряет полномочия сама.
- **Модели ↔ миграции** — расхождений нет; миграции идемпотентны (`_has_table`/`_create_index_once`), `env.py` берёт URL из `settings`.
- **Контракт frontend↔backend** — сквозная сверка всех `apiGet/apiPost` и читаемых полей расхождений не дала; есть собственный статический тест `test_frontend_backend_contract.py`.
- **Прокси** — owner-токен только на сервере, в клиентский бандл не попадает.
- **`exit_policy`** — каждый порог с обоснованием и номером сделки, на которой выведен.
