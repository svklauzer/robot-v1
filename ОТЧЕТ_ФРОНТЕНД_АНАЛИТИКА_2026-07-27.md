# Аудит фронтенда: аналитика

Проверил все витрины против фактических ответов бэкенда. Нашлось четыре
расхождения, из них одно принципиальное — метрика показывала не то, что
написано на карточке.

## 1. «MFE capture» показывала совсем другую величину

На карточке стояло `mfe_capture_rate` из `/analytics/signal-quality`. Читается
как «мы забираем N% предложенного хода». А в бэкенде это:

```python
mfe_capture_count += reason in {"adaptive_mfe_capture"}
...
"mfe_capture_rate": mfe_capture_count / lifecycle_count * 100
```

**Доля закрытий по одной конкретной ветке выхода.** К доле забранного пика
отношения не имеет. Добивал цвет: `good={mfe_capture_count > 0}` — одна
сделка через эту ветку красила карточку в зелёный.

Настоящий capture всё это время считался рядом, в `/analytics/mfe-mae`, но на
верхний уровень не выводился. Теперь выводится, с окном, медианой и размером
выборки; счётчик выходов через ветку остался припиской.

## 2. capture_rate ломался от одной сделки

```python
captured = [r["result_pct"] / r["mfe"] for r in bucket_rows if r["mfe"] >= 0.2]
sum(captured) / len(captured)
```

Среднее **отношений**. Сделка с малым MFE и крупным убытком даёт запредельное
отношение и в одиночку определяет бакет.

Боевые #264–#282, 14 сделок с MFE ≥ 0.2%. Сделка **#277**: MFE 0.29%,
результат −1.04% ⇒ **−356%**.

| метрика | значение |
|---|---|
| среднее отношений (было) | **12.9%** |
| портфельная sum/sum (стало) | **34.3%** |
| без одной сделки #277 | 38.4% |

Одна сделка из четырнадцати смещала метрику на 21 пункт. В бакетах
символ×режим, где обычно 1–3 сделки, метрика была нечитаемой.

Перешёл на портфельную долю `sum(result) / sum(MFE)` — она отвечает на нужный
вопрос: какую часть суммарно предложенного хода мы забрали. Рядом отдаётся
медиана и `capture_sample_count`: расхождение между ними = перекос выборки.

## 3. capture считался от завышенного результата

`result_pct` брался сырым, а у фантомных филлов он **выше собственного
максимума** — то есть capture > 100%. Добавил кламп `result_pct ≤ mfe_pct`:
закрытие не может быть лучше пика, это инвариант, а не эвристика.

**Что это меняет по существу:**

| | capture |
|---|---|
| было показано | 12.9% |
| без выброса, но с фантомами | 34.3% |
| **честно (кламп + портфельно)** | **18.2%** |

Реальная картина: **мы отдаём около четырёх пятых предложенного хода.** Это
самая важная цифра дня — она прямо про то, чем мы занимались: «не отдавать MFE».
Прежняя витрина эту проблему маскировала с двух сторон сразу.

## 4. Winrate считался от сырого PnL

```python
wins += 1 if net_pnl > 0 else 0
```

Фантомный филл — сделка, «закрытая» по цене выше собственного максимума —
попадала в победы. Слева на дашборде честный PnL, справа winrate от завышенного:
две соседние карточки про один период по разным правилам.

Добавлены `winrate_honest` / `wins_honest` / `losses_honest` /
`avg_net_pnl_honest_usdt`. Сырые поля оставлены для сверки с историей.

## 7. Сеть на `/health` — сделано

Две витрины инцидента 26.07 существовали только как эндпоинты.

**Доступность исходящей сети** (`/system/egress-history`). Доступность за окно,
число окон недоступности, худший DNS, разбивка по вердиктам и сам список окон —
с временными метками и хостами, то есть готовый текст для тикета. Окно
переключается: 6ч / 24ч / 3д / 7д.

Ключевое на витрине — **вердикт**, а не проценты:

| вердикт | что делать |
|---|---|
| `exchanges_unreachable` | биржи лежат, контрольные живы → менять хост или ставить прокси |
| `egress_down` | лежит всё, включая Cloudflare/Google → сторона платформы, `HTX_API_HOSTNAME` трогать бесполезно |

Именно эту разницу мы вчера выясняли полдня. Сырой код на экране её стирает —
поэтому вердикты переведены, и на это есть тест.

**Диагностика подключения** (`/system/exchange-diagnostics`). Постадийно
DNS → TCP → TLS → HTTP по каждому хосту, рядом контрольная группа, вердикт и
состояние размыкателя. Каждая стадия — отдельный чип с временем или ошибкой.

**Про нагрузку.** Страница обновляется каждые 5 секунд, и обе витрины туда
класть нельзя:

- `egress-history` читает журнал целиком → вынесена на отдельный интервал 60 с;
- `exchange-diagnostics` делает реальные зонды с таймаутом 8 с на хост →
  **строго по кнопке**. На автополлинге она держала бы воркер занятым — то есть
  инструмент диагностики простоя сам стал бы его причиной.

Тест проверяет и это: `runDiagnostics` не должен оказаться в `setInterval`.
