# Production Runbook

Операционная инструкция по выкатке и обслуживанию боевого контура. Коротко и по
делу: как накатывается схема, как проверить готовность к live, как проверить
резервное копирование.

## 1. Схема БД и миграции

Схема в проде создаётся ТОЛЬКО миграциями Alembic, а не приложением.

- В `docker-compose.prod.yml` есть отдельный сервис `api-migrate`, который
  выполняет `alembic upgrade head` и завершается. Основной `api` стартует лишь
  после него по условию `service_completed_successfully`.
- Переменная `DB_AUTO_CREATE_SCHEMA=false` — приложение НЕ вызывает
  `Base.metadata.create_all` на старте. Иначе SQLAlchemy создал бы таблицы в
  обход миграций, и состояние схемы разошлось бы с историей Alembic (типы
  колонок, индексы, дефолты — по коду модели, а не по ревизии).

Порядок выкатки:

1. Прогнать миграции (`api-migrate` / `alembic upgrade head`).
2. Убедиться, что ревизия совпадает с ожидаемой (`alembic current`).
3. Поднять `api`.

## 2. Готовность к live — `/system/readiness`

Перед включением реальных ордеров дёрнуть эндпоинт `/system/readiness`
(owner-токен). Он возвращает список блокеров: незаданные ключи биржи, отсутствие
Telegram-алертов владельца, рассогласование режимов, и — важно — кэп нотионала
ордера ниже типового размера позиции.

Пороговые предохранители перед live:

- `ROBOT_MODE=live` и `ENABLE_LIVE_ORDERS=true` (в paper остаётся paper).
- `LIVE_MAX_ORDER_NOTIONAL_USDT` — кэп нотионала ОДНОГО ордера; заведён в
  сайзинг, поэтому бумага и live берут один размер. Держать не ниже типового
  нотионала позиции.
- `ENABLE_FUTURES=true`, если используется плечо/своп-хедж.

`readiness` должен вернуть пустой список блокеров. Ненулевой список — go-live
запрещён до устранения причин.

## 3. Резервное копирование — smoke-проверка

Скрипт `scripts/db_backup_restore_smoke.sh` прогоняет полный цикл
`pg_dump → createdb → pg_restore → dropdb` на временной БД и печатает план.

Сухой прогон (без реальных операций, только план и проверка окружения):

```
bash scripts/db_backup_restore_smoke.sh --dry-run
```

Признак успеха — строка `backup_restore_smoke_status=ok` в конце вывода. Если её
нет, смотреть stdout/stderr: обычно причина в отсутствии `pg_dump`/`pg_restore`
в PATH или в переменных подключения.

Реальный прогон (без `--dry-run`) выполнять на копии, а не на боевой БД.

## 4. Откат

- Код: откат на предыдущий деплой (blueprint/образ).
- Схема: `alembic downgrade <ревизия>` только если миграция обратимая и это
  действительно нужно; чаще безопаснее откатить код к ревизии, совместимой с
  текущей схемой.
- Торговля: аварийный стоп — kill-switch (`/system/kill-switch`), затем
  `ENABLE_LIVE_ORDERS=false`.
